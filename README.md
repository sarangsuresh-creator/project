# STM32 mini data logger
## overview
I have developed a stm32f429zit6 based data logger system that uses ADC,DMA,Timer for setting sampling time,PWM for led brightness control,UART for realtime data logging and External interrupt for resume and pause of both data and pwm
## overall working
At 1st i have configured the timer for generating 1 KHz frequency to generate a timer of 1 ms.Then i am usimg this timer overflow to trigger the ADC conversion every 1 milli second.Then i have configured the DMA to store the data in a buffer inside RAM whenever a new coversion is completed by ADC. so upto this section  the CPU has nothing to do,everything is handled by hardware peripherals.for now the size of the buffer is given to be 16*4 bytes.Then comes the moving average filter where i am taking n = 8.That is i have divided the buffer into 8 + 8 section and i am using ADC HALF COMPLETE CALLBACK and  ADC COMPLETE CALLBACK for the DMA to determine whether the buffer is half filled or fully filled.the reason why i am using this method is because i can perform moving average filter on the 1st half when the dma is has completed the 1 st half and filling the second half and then i can perform average filter on the 2nd half when DMA is filling on the 1 st half.the reason why i am using this half and full method is since we have configured the DMA to be circular for ADC there may be chance of mixing the older data with new set of data because there is no any synchronization between DMA writing and CPU reading and in this, the speed of cpu exceeds that of DMA so DMA lags behind CPU.and also i have set the baudrate to be 115200 for uart so that it can leads over DMA.so in this particular configuration where the DMA is lagging behind both CPU and UART there comes the benefit of reading through the 1st half and the second half.

After the filtered data is being prepared we have to send this to UART and also use this value to control the brightness of led using PWM.Since the requirement says that the uart data should be in a readble format i am using the HAL_GetTick timer for send the uart data every 100 ms.now the filted data needs to be provided to PWM.
for that i need a timeperiod of 1ms and the duty cycle should be in the range of 0-1000 so a mapping equation is needed to be used for converting the 0-4095 range to 0-1000 range for duty cycle.and also since timer 3 is running on 1 khz so i used the same timer to generate the pwm signal.AT last an external interrupt is used to start and stop both the uart data logging + pwm.

## Design Choises
1) chosing ADC + DMA over ADC + interrupt :if we use DMA to transfer data from ADC to memory then we can free the CPU avoiding polling for every conversion saving the CPU clock cycles
2) ADC + Timer3 over ADC + continuous conversion : Timer  generates a 1khz frequency and the timer will trigger the ADC conversion every 1 ms.we can use the continuous conversion enable bit to continuously trigger the ADC but one cons is that adc will start conversion with every adc clock so it will be difficult for us to set precisely any frequency depending on the clock tree options
3) Filtering : here i used 8 + 8 DMA half and full call back method for smooth and precise filtering.suppose we are not using 8 + 8 method ,since we are using circular method for DMA to ADC transfer it will fill the 16 bit buffer in a continuous fashion.and if cpu try to take the average the while taking average the DMA can corrupt the old data with new data or other wise one solution is to use normal dma instead of circular dma but now the cpu has to do polling.so to overcome this the half dma callback will notify the cpu when half of the buffer is filled and complete call back dma will notify when buffer is fully filled.
4) chosing ISR : here i used UART_CALLBACK ISR to notify the CPU when every transmission is completed by UART-DMA. then used half and full complete DMA call backs for ADC conversion to determine whether the data has reached half way or full.then atlast used external interrupt to start and pause the uart data logging and pwm
5) button debouncing: there may be a chance that when we press the button multiple triggers may occur so to over come this we have to do some filtering methods.the one i chose is when an interrupt a flag is raised and also HAL_GetTick() timer current value is stored. then in the main function we check for the same edge state every 5ms for 10 concecutive times and if the result can be greater 7  then we can predict the button is actually pressed overcoming debouncing effect
